- **Help pass (agreed 2026-11-18):** every feature this fork has added gets its help and info text, and old help that no longer matches the app is corrected. - **Sharp scaling (agreed 2026-11-18):** a third SETTINGS scaling mode beside INTEGER (sharp but whole sizes only, so a 960x544 RG505 or a 1280x720 Smart Pro shows a small 1x picture) and FIT (fills, but blurry): SHARP enlarges by a whole number with crisp pixels, then shrinks smoothly to the largest size that fits, so the picture fills the screen and stays nearly as crisp. It lives in `shell/sdl/sdl-video.cpp`, which the Android app builds too (`native/CMakeLists.txt` adds it; `MainActivity` is an SDLActivity), so one change covers Windows, Linux, the handhelds and Android. It must work on every Android version the app supports (minSdk 26, Android 8.0, and up) and with SDL's software renderer fallback (it needs a render-target texture). The spec checks the Android touch buttons still get room beside the bigger picture, and whether SHARP becomes the default on any platform. It must look right with every theme, font and surface style in the appearance settings: it scales the finished picture, and any bars keep the theme's letterbox colour. Android's system bars stay as today (hidden, edge to edge; a swipe shows them over the app). No space is reserved for bars that won't hide unless a real device shows the problem.
- **Sound: master limiter (agreed 2026-11-18):** replace the always-on DaisySP limiter (`effects/primitives/daisysp/limiter.cpp`). Today it scales the whole mix by 0.7 and runs every sample through a soft-saturation curve, so a full mix leaves about 4 dB under full scale and slightly coloured; it reacts in under 0.5 ms with no look-ahead (bass distortion), releases over about 1 s (pumping), and limits left and right separately (the image shifts). New: a stereo-linked look-ahead limiter with its ceiling near 0 dBFS, transparent below it. Measure a real render first to confirm the -4 dB. The spec decides whether old songs can keep the old sound. Renders change, so the golden recordings are re-recorded.
- **Sound: sample interpolation (agreed 2026-11-18):** sample playback reads with linear interpolation (`sampler-voice.h` `Playhead::read`), so samples pitched up alias and pitched down go dull. Modes, from OpenMPT's resampler (BSD-3, fits GPL-3; its notice goes in THIRD-PARTY-NOTICES; ported only where it fits the float mixer): NONE, LINEAR (today's), CUBIC, SINC 8, SINC 8 LP. No separate Hermite (it would sound the same as CUBIC). **Saved in two places.** The song keeps its mode in the file; the device keeps a default. A new song starts with the device default; opening a song plays the song's mode; closing it and starting a new song goes back to the device default (opening a song never changes it). **Old songs** (no mode in the file) load as LINEAR, so they sound as they did; saving writes the mode into the file, and not saving changes nothing. **The SETTINGS row** changes the open song's mode. On a new song it first asks whether the choice is for this song only or the device default, with an info-text explanation; that is the only way to change the device default. **Device limit:** each device also has a highest mode it may play (a SETTINGS row). A song asking for more plays at the limit, keeps its saved mode, and says so on the status line (`INTERP LIMITED TO CUBIC`). The spec decides the factory device default (CUBIC suggested: clean and cheap everywhere) and each platform's factory limit, checks the sinc modes on the weakest handheld, and decides how renders and goldens pick the mode. The downsample effect keeps its own quantized read.
- **Sound: oversampled drive:** the DaisySP overdrive runs at the base rate, so high notes through heavy drive alias. Run the drive stage at 2x with a small up/down filter pair. The spec checks the CPU cost on the weakest handheld.
- **Fake stereo loads as mono (agreed 2026-11-19):** when a sample loads, a stereo file whose left and right channels are exactly the same is kept as one channel, halving its memory (samples are 32-bit float in RAM, about twice a 16-bit file). Only exact copies count, so nothing audible changes; the file on disk is untouched; the log notes it. The spec checks that pan and the instrument chain give bit-identical output for such a sample played as mono (stereo samples and mono samples take different paths in `engine-mix.cpp`), that the sample editor then shows it as mono, and that the goldens still match. No question when picking a file.
- **Save under a new name (agreed 2026-11-18):** when SAVE would write over an existing file (songs: only a *different* song, never the open one), ask `<THING> EXISTS - OVERWRITE?`. A overwrites. B opens the on-screen keyboard to type a new name; saving it goes through the same check again. Cancelling the keyboard goes back to where SAVE was pressed: nothing saved, nothing changed. No automatic `-2` numbering. One rule for **every save that writes a file**: songs, instrument presets (`.pti`), themes (`.ptt`), scales (`.pts`), grooves (`.ptg`), reverb (`.ptr`), delay (`.ptd`), and chords when the chord editor exists. Also a FILE RENAME onto a name that is taken. Fixed-name saves (the template, Studio's custom FX/master slots) and COLLECT (already asks) are reviewed in the spec. Sample SAVE-AS and RESAMPLE stay as they are (they number their files).
- **Wide mode (agreed 2026-11-19):** a SETTINGS choice between today's 4:3 (640x480, the default) and 16:9 (854x480, the same height, so text stays the same size), saved on the device. For the RG505, Odin, TrimUI Smart Pro, laptops and tablets; 4:3 handhelds stay as today. Goes after sharp scaling, which makes the picture fill the screen. Screens stay anchored in place, never centred, so nothing jumps between screens (the Studio may be centred). SONG and MIXER use the width for more tracks per page: under the 8-track setting tracks 9-16 show greyed, under 16 they are usable. PHRASE shows the other tracks' notes at the same rows, greyed, view only. CHAIN leaves its extra space empty. INSTRUMENT spreads out; the Studio fits more controls per page. Nothing exists only in wide mode: every control is reachable in 4:3 too, and the navigation side panel always shows (no true full-screen view). No phone rotation. Everything new follows every theme, font and surface style. The spec checks the Android touch buttons still get room, the screenshot goldens for the wide size, and whether switching applies at once or after a restart. Built before the chord editor, resample box and New Note Action, so their screens are made for both widths.
- **Chords on synths:** `CHD` plays its chord on the chord engines (P CHORD, P STRING MACHINE, G CHORD SWARM): one engine plays the chord's notes, taken from the same chord list as samples (snapped to the scale, with the voicing). 4 notes. Every other synth stays as today (root note only). Plaits' chord engine and G CHORD SWARM have built-in chord tables to replace with the chord's notes.
- **Chord editor:** the song's 16 chords become editable song data on a CHORD screen built like SCALE (next to SCALE and GROOVE): a NAME row cycling the built-in chords (kept as presets, `*` when edited), SAVE and LOAD of chord files (with the new-name rule above), one row per note. 4 notes. A song with no chord data loads today's 16 shapes in today's order, so old songs sound the same. `CHD`, HARMONY and chords on synths all read the song's chords. One built-in chord list for the whole app: today's 16 shapes plus the ones only Plaits' chord engine has (octave, fifth, 6/9, spread major 10th, dominant 7 flat 9, half-diminished, fully diminished, as 4-note shapes), offered as NAME presets; the 16 song slots still start as today's shapes in today's order.
- **Maqam microtones (agreed 2026-11-19):** each scale note's cents offset, already stored in songs and `.pts` files (`Scale::offset`, `songcore/model.h`, −2400..+2400 cents) but not played or shown today, becomes real. A note snapped by a scale plays with its degree's offset: exact on samples (each chord note too, through its own ratio) and on synths (they take a frequency); SoundFonts through TinySoundFont's per-channel tuning (`tsf_channel_set_tuning`, one channel per track), where a chord shares one tuning and a release tail shifts when the next note retunes, unless the spec adds a guarded per-note tuning to TinySoundFont; external MIDI only approximately (pitch bend). The SCALE screen gains a cents column per note. NAME gains maqam presets (Rast, Bayati, Saba, Sikah, Huzam, Hijaz, Nahawand, Kurd, Ajam and others) with standard offsets that can be adjusted for regional intonation. Phrases mark notes that sound shifted. Chords (`CHD`, the chord editor) follow the scale's offsets. A scale holds one version of each note; maqams that change mid-passage switch scales with `SCA`. Old songs are unchanged (every offset 0). The spec decides how the cents travel from the sequencer to the voices (notes are whole semitones there today; the event layout is checked against goldens) and writes the help.
- **Chord swarm engine (Hypersynth-style):** a new synth model that runs one Braids SAW SWARM (already vendored, MIT; 7 detuned saws, JP-8000 layout) per chord note: 4 notes, 28 saws. It reads `CHD` like the other chord engines (needs "Chords on synths" first). Knobs: detune (the swarm's own), brightness (its filter), stereo spread across the chord. A thin wrapper around existing Mutable code, like TrackWerk's other models, not a synth written from scratch.
- **Synth stereo output (agreed 2026-11-19):** a synth can hand the voice two channels instead of one (today `synth.next` returns one value, so every synth is mono). A stereo synth uses the instrument chain's existing stereo path (the one stereo WAVs and SoundFonts use: `chain.processStereo` in `engine-mix.cpp`); mono synths stay exactly as today, at the same CPU. First users: the electric piano's tremolo pan and the organ's rotary speaker (next item), then Rings and Elements, which already make stereo. Any future stereo synth plugs into the same path.

- **New Note Action (Impulse Tracker style):** what a note does when the next one starts on its track. Two INSTRUMENT rows: `NNA` CUT (default, today's behaviour) / OFF (plays its release) / FADE / CONT (keeps playing), and `DUP` (what the same note again does: off / cut / release / fade, so pads and hi-hats don't pile up). One new phrase command `NNA xy`: x acts on the notes already ringing in the background on this track (leave / cut / release / fade), y overrides the instrument for this note. `OFF` and `KIL` keep acting on the current note only (to confirm in the spec). Old notes ring in background voices; when there are none free, the quietest is dropped. Separate from the later voice-capacity setting in Settings (how many voices a device may use), which decides how many background voices there are.
- **Voice capacity setting (future):** a SETTINGS row for how many voices this device may play at once. NORMAL (the default) is exactly today's 8 song voices plus the preview voice, so small handhelds and existing songs are unchanged; higher steps let stronger devices (Windows, Android, strong handhelds) use more CPU. A device setting, not saved in the song. It pays for New Note Action's background voices and, later, chords on synths beyond the chord engines; when full, the quietest voice is dropped instead of the sound breaking up. The spec decides the steps per platform and whether the app warns when a song wants more voices than the device allows.
- **Resample options box + DRY:** RESAMPLE (a SONG selection, then A,A) first opens a small options box, then the name keyboard as today. This item builds the box and its first row, `DRY` OFF/ON. OFF (the default) is today's mix. ON renders the selected tracks with no reverb or delay returns, no master EQ, OTT, DUST or Studio master rack, no PERFORM filter and no master fader; it keeps the instruments' own sound and the track faders, and the safety limiter (the file is 16-bit). The box remembers its rows between uses. The status says `RESAMPLED DRY -> INST xx` when DRY was on.
- **Resample: normalise on render:** a row in the resample options box, `NORMALIZE` OFF/ON (OFF by default). ON raises the finished sample to a peak target (the sample editor's Peak Normalize, -1 dBFS unless the spec decides otherwise), so no trip to the sample editor.
- **Resample: load as instrument:** a row in the resample options box, `LOAD INST` ON/OFF (ON by default, today's behaviour). OFF only writes the WAV to the Resampled folder and leaves the instruments alone, with a status that names the file.
- **Resample: bit depth (agreed 2026-11-18):** a row in the resample options box, `BITS` 16 (default, today's) / 24 / 32F, the artist's choice. 16-bit gets TPDF dither instead of today's truncation (`songcore/wav_writer.h`). The spec decides whether the song's WAV export gets the same choice.

- **LSDJ song import (agreed 2026-11-19):** open LSDJ songs (.lsdsng / .sav) as a copy in TrackWerk's own format, as M8 songs are today (reference: ChooChooTracker (MIT, read 2026-11-19), `lsdj_format.h`). Best after the Game Boy chips item, so pulse, wave and noise instruments get the real chip sound. The result is close, not identical: LSDJ's own command and table behaviour is translated, drum kits live in the LSDJ program (ROM) and are not in the song file, so kits need the user's own kit samples, and the import writes a report of what changed, as the M8 import does.
- **MOD import (agreed 2026-11-19):** ProTracker / Amiga modules (4 tracks, some 6-8), the largest tracker archive there is: samples, notes and effects (arpeggio, slides, vibrato, volume slides, speed and tempo mapped to tempo and grooves). Fits 8 tracks today. The spec checks whether libopenmpt (BSD-3) exposes samples and patterns fully enough, or reads the format directly (it is simple and documented). Like every import: read into a copy, saved as `.ptp`, the original never written, and a report of what changed (commands translated to TrackWerk's, close but not always identical).
- **LittleGPTracker / picoTracker import (agreed 2026-11-19):** 8-track handheld trackers with the same song → chain → phrase model as TrackWerk, so songs come across nearly one-to-one, samples and instruments included. Like every import: read into a copy, saved as `.ptp`, the original never written, and a report of what changed (commands translated to TrackWerk's, close but not always identical).
- **FamiTracker import (agreed 2026-11-19):** NES songs (.ftm), 5 channels, after the Game Boy and NES chips item so they sound like the NES. Expansion-chip songs (VRC6, Namco 163 and others) that need more than 8 channels wait for 16 tracks, and chips we don't have are reported. Like every import: read into a copy, saved as `.ptp`, the original never written, and a report of what changed (commands translated to TrackWerk's, close but not always identical).
- **16 tracks (agreed 2026-11-18):** a SETTINGS row picks 8 (default) or 16 tracks; a new song gets the setting's count. A song's track count is saved in its file. The only thing that changes it: an 8-track song open under the 16 setting may use tracks 9-16, and once one of them has something in it the song becomes a 16-track song when saved. Opening, playing or saving it without using tracks 9-16 leaves it at 8. **Opening a 16-track song while the setting is 8** asks first, on every device: the song uses 16 tracks, your setting is 8, switch to 16? On weak devices (the Linux handhelds: Brick, RGB20S, Miyoo Mini/Plus and the other PortMaster targets) the box also explains that the device may not play the song fully, with sound problems, if the CPU runs out; Windows, Linux desktop and Android don't show that line. A switches the setting to 16 and loads the song. B cancels: the song is not loaded, and the song that was open stays exactly as it was (not saved, not edited). Opening an 8-track song while the setting is 16 shows no box. **Pages:** SONG, MIXER and any screen whose tracks don't fit (on 4:3, or past the screen's width) show them a page at a time; moving the cursor past the last track on the page turns to the next page, the way the screen map's letters move between screens, and a small arrow on the left or right shows there is another page that way. Open for the spec: what the preview lane (today track 8 + 1) becomes, MIDI and stems for tracks 9-16, and the voice count (16 song voices + preview). Mapped earlier: about 120 places in the code assume 8 tracks; the file format already allows any number.
- **S3M import (agreed 2026-11-19, needs 16 tracks):** Scream Tracker 3 modules (most use 8-16 channels), sample-based. Songs with more than 16 channels are refused or trimmed with a report; the spec decides. Like every import: read into a copy, saved as `.ptp`, the original never written, and a report of what changed (commands translated to TrackWerk's, close but not always identical).
- **XM import (agreed 2026-11-19, needs 16 tracks):** FastTracker 2 modules (most use 8-16 channels): samples, instruments with envelopes (mapped to TrackWerk's envelopes), notes and effects. More than 16 channels handled as for S3M. Like every import: read into a copy, saved as `.ptp`, the original never written, and a report of what changed (commands translated to TrackWerk's, close but not always identical).
- **MIDI file import (agreed 2026-11-19, needs 16 tracks):** standard MIDI files (.mid): 16 channels map to 16 tracks, played with SoundFonts (General MIDI), notes, velocities, program changes and tempo turned into phrases and chains. The spec decides how note lengths and overlapping notes on one channel (chords) become phrase steps, `OFF` and `CHD`. Like every import: read into a copy, saved as `.ptp`, the original never written, and a report of what changed (commands translated to TrackWerk's, close but not always identical).
- **IT import (agreed 2026-11-19, needs 16 tracks and New Note Action):** Impulse Tracker modules, the richest classic format: samples, instruments, envelopes and New Note Action. Songs that use more than 16 channels can't fully fit and are reported. Like every import: read into a copy, saved as `.ptp`, the original never written, and a report of what changed (commands translated to TrackWerk's, close but not always identical).
- **Furnace import (agreed 2026-11-19, needs 16 tracks and the chip synths):** Furnace chip-tracker songs (.fur, also older DefleMask songs), today's biggest chiptune community. Channels map to the chip models on the roadmap (AY, SN76489, YM2612 and the other ymfm chips, Game Boy, NES); chips we don't have are reported. Like every import: read into a copy, saved as `.ptp`, the original never written, and a report of what changed (commands translated to TrackWerk's, close but not always identical).
- **Synth voices on spare cores (future, agreed 2026-11-18):** the audio thread stays in charge; each block, synth voices go on a work list that idle helper threads may take, and the audio thread takes whatever is left itself, so it never waits on a helper. Each voice renders into its own buffer and the mix sums them in today's fixed order, so the output is bit-identical with any number of helpers. With no spare cores (or the setting off) nothing changes. Needs: synth voices rendered per block instead of per sample (`engine-mix.cpp` calls `synth.next` per sample today), per-voice meters, scopes and send sums merged after, and timing tests on every platform. Build after the sound items and New Note Action, and only when real devices run short of CPU (PERFORM's PEAK meter). Offline renders could use every core first, with no timing risk.

If the app changes enough that we release our own version instead of staying linked to upstream, we write our own guide then, with screenshots from the app's headless screenshot path. Until then, nothing here.
