- **Refuse songs from a newer TrackWerk (agreed 2026-11-19):** today the loader reads a song's `version` but never refuses a newer one (`songcore/project_io.h`), so an older app would open a newer song, silently drop what it doesn't know, and a SAVE would lose it. Add the check now: a song whose `version` is newer than this app understands is refused with `MADE WITH A NEWER TRACKWERK` and the open song stays as it was. Every later change to the song format raises `version`. Small, and worth doing early so as many released versions as possible carry it; `.pt16` covers the 16-track change on its own.
- **Tempo-change command `TPO` (agreed 2026-11-19):** a phrase command that sets the song tempo from that step (for ritardandos, section changes, half-time drops); the MOD, XM and IT importers need it for their speed and tempo commands. None of our 53 commands changes tempo today (grooves only change swing), and ChooChooTracker (MIT, read 2026-11-19) has none either. Small. Help: its SELECT and FX help entries and the manual.
- **Help pass (agreed 2026-11-18):** every feature this fork has added gets its help and info text, and old help that no longer matches the app is corrected. Covers: the latency row in Settings (today it has no entry by design: decide whether it gets one), the VI screen and its VISUALIZER row (check the existing entries), audit batch 1's new boxes and messages (LOAD discard, SAVE overwrite, damaged-file refusals), the name keyboard's first-B rule, and the two known gaps: SONG's help gains "A,A on a selection resamples it", PHRASE's help says B+LEFT/RIGHT goes to the next track's phrase (under NAV = SONG). Where: `source/native/ui/help_text.h` (SELECT help), `fx_helper.h` (effect commands), `studio_help.cpp`, plus `source/docs/manual-en.md` and `source/docs/quick-start-guide.md`. Every help line is checked against what the code does now, not against older docs.
- **Sharp scaling (agreed 2026-11-18):** a third SETTINGS scaling mode beside INTEGER (sharp but whole sizes only, so a 960x544 RG505 or a 1280x720 Smart Pro shows a small 1x picture) and FIT (fills, but blurry): SHARP enlarges by a whole number with crisp pixels, then shrinks smoothly to the largest size that fits, so the picture fills the screen and stays nearly as crisp. It lives in `shell/sdl/sdl-video.cpp`, which the Android app builds too (`native/CMakeLists.txt` adds it; `MainActivity` is an SDLActivity), so one change covers Windows, Linux, the handhelds and Android. It must work on every Android version the app supports (minSdk 26, Android 8.0, and up) and with SDL's software renderer fallback (it needs a render-target texture). The spec checks the Android touch buttons still get room beside the bigger picture, and whether SHARP becomes the default on any platform. It must look right with every theme, font and surface style in the appearance settings: it scales the finished picture, and any bars keep the theme's letterbox colour. Android's system bars stay as today (hidden, edge to edge; a swipe shows them over the app). No space is reserved for bars that won't hide unless a real device shows the problem.
- **Sound: master limiter (agreed 2026-11-18):** replace the always-on DaisySP limiter (`effects/primitives/daisysp/limiter.cpp`). Today it scales the whole mix by 0.7 and runs every sample through a soft-saturation curve, so a full mix leaves about 4 dB under full scale and slightly coloured; it reacts in under 0.5 ms with no look-ahead (bass distortion), releases over about 1 s (pumping), and limits left and right separately (the image shifts). New: a stereo-linked look-ahead limiter with its ceiling near 0 dBFS, transparent below it. Measure a real render first to confirm the -4 dB. The spec decides whether old songs can keep the old sound. Renders change, so the golden recordings are re-recorded.
- **Sound: sample interpolation (agreed 2026-11-18):** sample playback reads with linear interpolation (`sampler-voice.h` `Playhead::read`), so samples pitched up alias and pitched down go dull. Modes, from OpenMPT's resampler (BSD-3, fits GPL-3; its notice goes in THIRD-PARTY-NOTICES; ported only where it fits the float mixer): NONE, LINEAR (today's), CUBIC, SINC 8, SINC 8 LP. No separate Hermite (it would sound the same as CUBIC). **Saved in two places.** The song keeps its mode in the file; the device keeps a default. A new song starts with the device default; opening a song plays the song's mode; closing it and starting a new song goes back to the device default (opening a song never changes it). **Old songs** (no mode in the file) load as LINEAR, so they sound as they did; saving writes the mode into the file, and not saving changes nothing. **The SETTINGS row** changes the open song's mode. On a new song it first asks whether the choice is for this song only or the device default, with an info-text explanation; that is the only way to change the device default. **Device limit:** each device also has a highest mode it may play (a SETTINGS row). A song asking for more plays at the limit, keeps its saved mode, and says so on the status line (`INTERP LIMITED TO CUBIC`). The spec decides the factory device default (CUBIC suggested: clean and cheap everywhere) and each platform's factory limit, checks the sinc modes on the weakest handheld, and decides how renders and goldens pick the mode. The downsample effect keeps its own quantized read.
- **Sound: oversampled drive:** the DaisySP overdrive runs at the base rate, so high notes through heavy drive alias. Run the drive stage at 2x with a small up/down filter pair. The spec checks the CPU cost on the weakest handheld.
- **Fake stereo loads as mono (agreed 2026-11-19):** when a sample loads, a stereo file whose left and right channels are exactly the same is kept as one channel, halving its memory (samples are 32-bit float in RAM, about twice a 16-bit file). Only exact copies count, so nothing audible changes; the file on disk is untouched; the log notes it. The spec checks that pan and the instrument chain give bit-identical output for such a sample played as mono (stereo samples and mono samples take different paths in `engine-mix.cpp`), that the sample editor then shows it as mono, and that the goldens still match. No question when picking a file.
- **Phrase commands from ChooChooTracker (agreed 2026-11-19):** ChooChooTracker (MIT, read 2026-11-19) has 179 commands against our 53; most are tied to its own synths and chips and arrive with those items (see the synth items, layer, inserts, Advanced Synth Studio). The general ones we lack, each added with its SELECT help, FX helper line and manual entry, names to be settled in the spec: **VSL** volume slide (changes volume by an amount per step, continuously); **PRO** probability (the row plays with a 0-100 % chance; conditions on a row combine); **RNN** random note (plays a random note: mode and range); **RNS** random slice (plays a random slice in slice mode); **EUC** Euclidean retrigger (X hits spread over Y+1 rows, looping, until a new note, OFF, KIL or EUC); **REP / RTO** repeat the previous FX with a signed step per row, between limits (ramps without typing every row); **SPD** per-track speed (×1, ×2, ÷2, kept until the next SPD: half-time or double-time on one track); **SLE** smoothing for parameter changes (00 instant, else a glide in ticks, for synth and engine commands); **GGR** global groove (one groove for every track at once; ours `GRV` is per track); **SNG** song hop (jump N rows in the song); **TBX / TXH** a second, auxiliary table per note and its hop (two tables running at once); **TPN** track pan (sets the track's mixer pan, kept until changed; ours `PAN` is per note); **EAT / EDC / ESU / ERL / ESH** envelope attack, decay, sustain, release and shape for this note; **M1A-M4x** modulation slot commands (offset a mod slot's amount and its parameters); **MRT / MKL** retrigger or stop chosen modulation slots; **SEN** sample end for this note; **SLP** sample playback mode for this note (forward, reverse, loop, ping-pong); **SSP** sample speed 0-500 %; **NOF** note release after N ticks (their `OFF`; ours `KIL` cuts, so the spec checks whether a soft release command already exists before adding it). Already covered by ours (not added): RET → `RPT`, DEL → `LAT`, SST/STA → `OFF`, SCL → `SCA`/`SCG`, CRD → `CHD`, BEG/END → `AUS`/`AUF`, RSN/DSN → `REV`/`DEL`, MC1-4 → `CCA`-`CCD`, MOD → `NTH` (the spec checks NTH covers pass A of B), PIT, FIN, VOL, PAN, SLI, NTH. Their help text (`tracker/src/screens/help.cpp`) is a reference for ours.
- **Drumlab: manual sequencing and layout (agreed 2026-11-19):** Drumlab (Studio tab, `ui/drumlab.cpp`) becomes a drum sequencer you can also fill by hand. **CLEAR** next to GENERATE starts an empty grid, so Step Edit no longer needs Generate first. **Empty lanes are allowed:** a SLOT can be `--` (no instrument), and a lane with no loaded sound is simply silent, skipped by Generate, Preview and Apply instead of blocking them; the active-lane minimum drops from 5 to 1. **Two pages:** SOURCES (the lanes: slot, lock, rhythm fields) and GROOVE (style, lanes, steps, density, variation, swing, humanize, fill, seed, map X/Y/chaos), switched with **L+LEFT/RIGHT** outside Step Edit; GENERATE / PREVIEW / APPLY sit on both. L or R alone still turns the 16-step bar. **Step Edit:** **L+DOWN** loops the preview (instead of A+DOWN; START stays the song's play), A tapped toggles a hit, **A+UP/DOWN** sets the hit's velocity, **A+LEFT/RIGHT** its timing nudge (0..11 ticks); both already stored and written by Apply. Checked 2026-11-19: L+arrows are unused in the Studio (L+SELECT is the Punch chord, L+R+START live resample), and the Studio already swallows a shoulder's release after a combo. Later, in its own step: chance (`CHA`), ratchets (`RPT`) and pitch (`PIT`) per step.
- **Piano roll (agreed 2026-11-19):** an optional piano-roll view of one phrase (one bar, 16 steps) for people who'd rather draw than type, opened from PHRASE with a shortcut and from the Studio. It is another way to enter the same phrase data, nothing new is stored: note → NOTE, velocity → VOL, note length → `OFF` at its end (or the next note), nudge off the grid → `LAT`, as Drumlab writes them. Built on Drumlab's Step Edit grid (cursor, A to place/remove, undo/redo, looping preview, apply), with pitch rows instead of lanes, scrolling through octaves; rows outside the scale dimmed, maqam offsets shown. Effects stay in PHRASE and are left untouched. A track plays one note at a time, so notes can't overlap; instead a **CHORDS** tool draws a whole chord: pick a chord from the song's chord list (today's 16 shapes, or the chord editor's when it exists) and a voicing, place it on a root, and Apply writes the root note plus `CHD xy` (chord and voicing are per note, so chords can change on every step). The roll draws the notes as they will really sound (snapped to the scale, as `chord_notes()` does), refuses overlapping notes that aren't a chord from the list, and warns when the track's instrument can't play chords (until "Chords on synths", only samples, SoundFonts and the chord engines). Same Drumlab-style keys: A tapped places or removes, A+UP/DOWN velocity, A+LEFT/RIGHT length, L+DOWN preview; touch drawing on Android. Searched 2026-11-19: no lightweight C++ piano-roll library fits TrackWerk's canvas and gamepad input, so it reuses Drumlab's grid instead. **With New Note Action (agreed 2026-11-19, once that item exists):** overlapping notes become possible: a note drawn over a still-ringing one makes the earlier note carry on in the background, written as the later note's `NNA` (its y: continue, release or fade), and a background note's drawn end becomes a release or fade of the background notes (`NNA x`) on the step where it ends. Where an overlap can't be written exactly (several background notes ending at different steps, or more background notes than the device's voices), the roll says so before Apply. Until then, overlaps are refused as above.
- **Save under a new name (agreed 2026-11-18):** when SAVE would write over an existing file (songs: only a *different* song, never the open one), ask `<THING> EXISTS - OVERWRITE?`. A overwrites. B opens the on-screen keyboard to type a new name; saving it goes through the same check again. Cancelling the keyboard goes back to where SAVE was pressed: nothing saved, nothing changed. No automatic `-2` numbering. One rule for **every save that writes a file**: songs, instrument presets (`.pti`), themes (`.ptt`), scales (`.pts`), grooves (`.ptg`), reverb (`.ptr`), delay (`.ptd`), and chords when the chord editor exists. Also a FILE RENAME onto a name that is taken. Fixed-name saves (the template, Studio's custom FX/master slots) and COLLECT (already asks) are reviewed in the spec. Sample SAVE-AS and RESAMPLE stay as they are (they number their files).
- **Wide mode (agreed 2026-11-19):** a SETTINGS choice between today's 4:3 (640x480, the default) and 16:9 (854x480, the same height, so text stays the same size), saved on the device. For the RG505, Odin, TrimUI Smart Pro, laptops and tablets; 4:3 handhelds stay as today. Goes after sharp scaling, which makes the picture fill the screen. Screens stay anchored in place, never centred, so nothing jumps between screens (the Studio may be centred). SONG and MIXER use the width for more tracks per page: under the 8-track setting tracks 9-16 show greyed, under 16 they are usable. PHRASE shows the other tracks' notes at the same rows, greyed, view only. CHAIN leaves its extra space empty. INSTRUMENT spreads out; the Studio fits more controls per page. Nothing exists only in wide mode: every control is reachable in 4:3 too, and the navigation side panel always shows (no true full-screen view). No phone rotation. Everything new follows every theme, font and surface style. The spec checks the Android touch buttons still get room, the screenshot goldens for the wide size, and whether switching applies at once or after a restart. Built before the chord editor, resample box and New Note Action, so their screens are made for both widths.
- **Chords on synths:** `CHD` plays its chord on the chord engines (P CHORD, P STRING MACHINE, G CHORD SWARM): one engine plays the chord's notes, taken from the same chord list as samples (snapped to the scale, with the voicing). 4 notes. Every other synth stays as today (root note only). Plaits' chord engine and G CHORD SWARM have built-in chord tables to replace with the chord's notes.
- **Chord editor:** the song's 16 chords become editable song data on a CHORD screen built like SCALE (next to SCALE and GROOVE): a NAME row cycling the built-in chords (kept as presets, `*` when edited), SAVE and LOAD of chord files (with the new-name rule above), one row per note. 4 notes. A song with no chord data loads today's 16 shapes in today's order, so old songs sound the same. `CHD`, HARMONY and chords on synths all read the song's chords. One built-in chord list for the whole app: today's 16 shapes plus the ones only Plaits' chord engine has (octave, fifth, 6/9, spread major 10th, dominant 7 flat 9, half-diminished, fully diminished, as 4-note shapes), offered as NAME presets; the 16 song slots still start as today's shapes in today's order.
- **Maqam microtones (agreed 2026-11-19):** each scale note's cents offset, already stored in songs and `.pts` files (`Scale::offset`, `songcore/model.h`, −2400..+2400 cents) but not played or shown today, becomes real. A note snapped by a scale plays with its degree's offset: exact on samples (each chord note too, through its own ratio) and on synths (they take a frequency); SoundFonts through TinySoundFont's per-channel tuning (`tsf_channel_set_tuning`, one channel per track), where a chord shares one tuning and a release tail shifts when the next note retunes, unless the spec adds a guarded per-note tuning to TinySoundFont; external MIDI only approximately (pitch bend). The SCALE screen gains a cents column per note. NAME gains maqam presets (Rast, Bayati, Saba, Sikah, Huzam, Hijaz, Nahawand, Kurd, Ajam and others) with standard offsets that can be adjusted for regional intonation. Phrases mark notes that sound shifted. Chords (`CHD`, the chord editor) follow the scale's offsets. A scale holds one version of each note; maqams that change mid-passage switch scales with `SCA`. Old songs are unchanged (every offset 0). The spec decides how the cents travel from the sequencer to the voices (notes are whole semitones there today; the event layout is checked against goldens) and writes the help.
- **Chord swarm engine (Hypersynth-style):** a new synth model that runs one Braids SAW SWARM (already vendored, MIT; 7 detuned saws, JP-8000 layout) per chord note: 4 notes, 28 saws. It reads `CHD` like the other chord engines (needs "Chords on synths" first). Knobs: detune (the swarm's own), brightness (its filter), stereo spread across the chord. A thin wrapper around existing Mutable code, like TrackWerk's other models, not a synth written from scratch.
- **Synth stereo output (agreed 2026-11-19):** a synth can hand the voice two channels instead of one (today `synth.next` returns one value, so every synth is mono). A stereo synth uses the instrument chain's existing stereo path (the one stereo WAVs and SoundFonts use: `chain.processStereo` in `engine-mix.cpp`); mono synths stay exactly as today, at the same CPU. First users: the electric piano's tremolo pan and the organ's rotary speaker (next item), then Rings and Elements, which already make stereo. Any future stereo synth plugs into the same path.
- **Synth: acid bass (agreed 2026-11-18):** a TB-303-style model from **Open303** (Robin Schmidt, MIT): its filter, accent and slide, light on CPU (about one oscillator and one filter per note). Slide maps to the existing pitch slide or legato; the spec decides how accent is written (a phrase command or velocity). Licence and CPU confirmed in the spec; notice in THIRD-PARTY-NOTICES. **Shortcut:** ChooChooTracker (github.com/paiheulevrai/Choochootracker, MIT, read 2026-11-19) ships Open303 and an acid voice built on it (`chipnomad_lib/synth/achchid_voice.cpp`: Open303 filter, Braids oscillators, a soft-clip-to-fold shaper, accent and slide), a model for this item. Their adapter is a shortcut, not the spec: the spec checks it exposes every control of the original engine and fits our real-time rules, and adds what it leaves out.
- **Synth: electric piano and organ (agreed 2026-11-18):** two models. Electric piano from **mda ePiano** (Paul Kellett, MIT; Rhodes-style from small built-in samples, very light). Drawbar organ from **setBfree** (GPL-2.0-or-later, fits GPL-3; drawbars and rotary speaker), checked on the weakest handheld before it goes in, with a lighter fallback (no rotary, or fewer voices) if it is too heavy there. Licences confirmed in the spec; notices in THIRD-PARTY-NOTICES.
- **Advanced Synth Studio (agreed 2026-11-19):** the Studio's synth page stays as it is (model, preset, macros); an ADVANCED button opens only the loaded synth with its full controls, on as many pages as it needs: what a professional VST3 would expose, every control that changes the sound and nothing purely technical. Known gaps: editing FM SYSEX's six operators, and Plaits' built-in envelope to timbre, morph and FM (fixed at zero today). The spec decides whether envelopes, LFOs or phrase commands may move synth controls (not possible today), and grows the song's synth settings past today's 16 per instrument so old songs load and sound the same. The same values give the same sound as today's rows; only controls fixed in the code today add new sound. **One set of values (agreed 2026-11-19):** the Advanced page shows everything for that synth, including what the main Studio pages already show (macros, engine params, and the instrument's filter, drive, level, pan, tune and ADSR, which are the instrument's own settings, the same values as on INSTRUMENT and MODS), and both pages edit the same values, so a change on one shows on the other and no switching back is needed. A synth's own envelopes (DX7 operator envelopes, Plaits' LPG decay, DCO POLY's envelope) are separate controls that act before the instrument's ADSR, and the page labels them so. Both FM SYSEX and the Dexed DX7 get their full controls here. **Synth control commands (agreed 2026-11-19):** phrase commands that set a synth's macros A/B/C and its params from a phrase step (absolute), with optional smoothing, so timbre, morph and the rest can move inside a song; ChooChooTracker (MIT, read 2026-11-19) has one set per engine (Braids `BMD/BTM/BCL`, Plaits `PMD/PHA/PTM/PMO/PAX`, Plaits trigger decay and colour `TDC/TCL`, FM operator commands, and so on). The spec decides one generic set (macro and param number) or per-engine sets, and the engines imported from ChooChooTracker (MIT, read 2026-11-19) bring their commands along.
- **Synth: DX7 from Dexed (agreed 2026-11-19):** a new 6-operator FM model built on Dexed's sound engine (msfa, Apache 2.0, from Music Synthesizer for Android; Dexed itself is GPL-3; notices in THIRD-PARTY-NOTICES), very close to a real DX7 and light on CPU (msfa was written for 2012-era phones). **Source (checked 2026-11-19):** the voice engine is `source/msfa/` (about 25 plain C++ files, Apache 2.0, no JUCE): note, operators, envelopes, LFO, pitch envelope, tables; `source/core/` reads cartridges. `source/engine/` holds two alternative cores, EngineMkI (the original DX7 Mark I chip's character) and EngineOpl (Yamaha OPL, the AdLib/Sound Blaster chip), both GPL-3. - **Synth: your own wavetables (agreed 2026-11-19):** no new model: P WAVETABLE's 4th bank plays a WAV you load, from a row on its Advanced page (needs the item above). The file is stored with the song like a sample. **Reference:** ChooChooTracker (github.com/paiheulevrai/Choochootracker, MIT, read 2026-11-19) loads single-cycle WAVs and user wavetables with no frame limit (`scwf_voice.cpp`, `sr_wavetable_loader.cpp`), but without band-limiting as far as read; the spec compares it with the Plaits route.

- **Synth: Monk vocal synth (agreed 2026-11-19):** MonkSynth by JonET (MIT): a chanting vocal synth with 10-voice unison and its own stereo delay, all 16 original parameters, as packaged in ChooChooTracker (github.com/paiheulevrai/Choochootracker, MIT, read 2026-11-19) (`external/monksynth`, `monk_voice.cpp`). A different flavour from FORMANT CHOIR. Its stereo delay wants the synth stereo output item. Their adapter is a shortcut, not the spec: the spec checks it exposes every control of the original engine and fits our real-time rules, and adds what it leaves out.
- **Synth: Sophie metallic percussion (agreed 2026-11-19):** the Sophie metallic-percussion core (Matt Estela, MIT, via DigiSophie), as used in ChooChooTracker (github.com/paiheulevrai/Choochootracker, MIT, read 2026-11-19) (`external/digisophie`, inside `drum_synth_voice.cpp`). Their adapter is a shortcut, not the spec: the spec checks it exposes every control of the original engine and fits our real-time rules, and adds what it leaves out.
- **Synth: MME cross-modulation (agreed 2026-11-19):** ChooChooTracker (github.com/paiheulevrai/Choochootracker, MIT, read 2026-11-19)'s MME voice (`mme_voice.cpp`, MIT): Mutable Warps' ring modulation, wavefolding, XOR/comparator and filter-bank vocoder as a playable synth voice. The spec checks it against the Warps code we already vendor. Their adapter is a shortcut, not the spec: the spec checks it exposes every control of the original engine and fits our real-time rules, and adds what it leaves out.
- **Synth: OB-Xd (agreed 2026-11-19):** an Oberheim OB-X emulation (GPL-3): 80s brassy stabs, fat pads and its filter, a different analogue flavour from DCO POLY and the VA models. Only its voice code (oscillators, filter, envelopes) is taken, not the JUCE plugin. Moderate CPU: fine on phones and laptops, heavier on the smallest handhelds, which get a lighter fallback if needed. Licence and separability confirmed in the spec.
- **New Note Action (Impulse Tracker style):** what a note does when the next one starts on its track. Two INSTRUMENT rows: `NNA` CUT (default, today's behaviour) / OFF (plays its release) / FADE / CONT (keeps playing), and `DUP` (what the same note again does: off / cut / release / fade, so pads and hi-hats don't pile up). One new phrase command `NNA xy`: x acts on the notes already ringing in the background on this track (leave / cut / release / fade), y overrides the instrument for this note. `OFF` and `KIL` keep acting on the current note only (to confirm in the spec). Old notes ring in background voices; when there are none free, the quietest is dropped. Separate from the later voice-capacity setting in Settings (how many voices a device may use), which decides how many background voices there are.
- **Voice capacity setting (future):** a SETTINGS row for how many voices this device may play at once. NORMAL (the default) is exactly today's 8 song voices plus the preview voice, so small handhelds and existing songs are unchanged; higher steps let stronger devices (Windows, Android, strong handhelds) use more CPU. A device setting, not saved in the song. It pays for New Note Action's background voices and, later, chords on synths beyond the chord engines; when full, the quietest voice is dropped instead of the sound breaking up. The spec decides the steps per platform and whether the app warns when a song wants more voices than the device allows.
- **Resample options box + DRY:** RESAMPLE (a SONG selection, then A,A) first opens a small options box, then the name keyboard as today. This item builds the box and its first row, `DRY` OFF/ON. OFF (the default) is today's mix. ON renders the selected tracks with no reverb or delay returns, no master EQ, OTT, DUST or Studio master rack, no PERFORM filter and no master fader; it keeps the instruments' own sound and the track faders, and the safety limiter (the file is 16-bit). The box remembers its rows between uses. The status says `RESAMPLED DRY -> INST xx` when DRY was on.
- **Resample: normalise on render:** a row in the resample options box, `NORMALIZE` OFF/ON (OFF by default). ON raises the finished sample to a peak target (the sample editor's Peak Normalize, -1 dBFS unless the spec decides otherwise), so no trip to the sample editor.
- **Resample: load as instrument:** a row in the resample options box, `LOAD INST` ON/OFF (ON by default, today's behaviour). OFF only writes the WAV to the Resampled folder and leaves the instruments alone, with a status that names the file.
- **Resample: bit depth (agreed 2026-11-18):** a row in the resample options box, `BITS` 16 (default, today's) / 24 / 32F, the artist's choice. 16-bit gets TPDF dither instead of today's truncation (`songcore/wav_writer.h`). The spec decides whether the song's WAV export gets the same choice.
- **Per-track insert effects (agreed 2026-11-19):** each track gets its own effect slot(s), after its instruments and before the sends: compressor, distortion, tape, chorus, flanger, phaser, rotary, saturation, bitcrusher, parametric EQ, trance gate, Beads granular, formant, stereo width (the list in ChooChooTracker (MIT, read 2026-11-19), `chipnomad_lib/insert_fx.*`, `external/insert_fx`: Airwindows, OTT, TapeScam, JM Formant, Beads; each licence confirmed in the spec). The spec decides how many slots per track, where they are edited (MIXER), their automation from phrases, and the CPU budget per device. **Sidechain (agreed 2026-11-19):** the insert compressor can listen to other tracks (a sidechain source per track, and tracks left out on the master), so the kick ducks the bass for real; ChooChooTracker (MIT, read 2026-11-19) does this (`insert_fx.cpp`, `sidechainSourceMask`). **Phrase commands** set each insert's parameters (their `F11`-`F28`).
- **Layer instrument (agreed 2026-11-19):** an instrument that plays up to 3 other instruments on one note, each with its own transpose (as in ChooChooTracker (MIT, read 2026-11-19), `InstrumentType::Layer`), for thick sounds without spending tracks. The spec decides how it counts against voices and how it shows on INSTRUMENT. **Phrase commands** set each layer's tuning and level per note (their `L1C`/`L1V`-`L3C`/`L3V`).
- **Live audio input on a track (agreed 2026-11-19):** a mic or line input played through a track in real time, with that track's effects, volume and sends (as in ChooChooTracker (MIT, read 2026-11-19), `audio_input_voice.h`). Today recording only goes to a sample, and the Linux recorder has no path to the output on purpose. The spec handles feedback and latency (headphones advised) and which platforms have it.
- **Recording on Windows (agreed 2026-11-19):** the Windows build has no recorder; Linux and Android implement the shared `CaptureBackend` (`native/ui/audio_capture.h`). Add a Windows one (SDL capture, as the Linux one uses), so mic, line-in and USB interfaces record into samples there too.
- **Track bounce (agreed 2026-11-19):** record one track to a sample while the song plays, including live tweaks (as in ChooChooTracker (MIT, read 2026-11-19), `track_bounce.*`: a lock-free ring from the audio thread to a writer thread). RESAMPLE stays the offline way.
- **Live stick (agreed 2026-11-19):** a handheld's analogue stick as a performance controller (filter, macros, PERFORM targets), as in ChooChooTracker (MIT, read 2026-11-19) (`chipnomad_lib_live_stick.*`). The spec maps it onto PERFORM's controls.
- **Automation recording (agreed 2026-11-19):** with record armed and the song playing, moving a mapped knob writes its movement into the playing phrase as that parameter's command on each step it passes, so playback repeats it; smooth stretches can be tidied into an `AUS`/`AUF` ramp. Works with MIDI controllers learned with R + knob (`songcore/midi_map.h`) now, and with the handheld's analogue stick once "Live stick" exists. Records anything a knob can be learned to and a phrase command can set (today: volume, pan, sends, track and master faders, filter, drive, fine tune, delay time, EQ slots; later the envelope, synth control and insert commands). Today knob moves change the live value only, and PERFORM's controls are not recorded. The spec handles: one value per step (finer movement belongs in tables), the three effect columns (never overwrite the user's commands: use a free column or warn), phrases used elsewhere in the song (warn, or record into a copy), undo through PHRASE's history, and whether PERFORM's knobs record too.
- **LSDJ song import (agreed 2026-11-19):** open LSDJ songs (.lsdsng / .sav) as a copy in TrackWerk's own format, as M8 songs are today (reference: ChooChooTracker (MIT, read 2026-11-19), `lsdj_format.h`). Best after the Game Boy chips item, so pulse, wave and noise instruments get the real chip sound. The result is close, not identical: LSDJ's own command and table behaviour is translated, drum kits live in the LSDJ program (ROM) and are not in the song file, so kits need the user's own kit samples, and the import writes a report of what changed, as the M8 import does.
- **MOD import (agreed 2026-11-19):** ProTracker / Amiga modules (4 tracks, some 6-8), the largest tracker archive there is: samples, notes and effects (arpeggio, slides, vibrato, volume slides, speed and tempo mapped to tempo and grooves). Fits 8 tracks today. The spec checks whether libopenmpt (BSD-3) exposes samples and patterns fully enough, or reads the format directly (it is simple and documented). Like every import: read into a copy, saved as `.ptp`, the original never written, and a report of what changed (commands translated to TrackWerk's, close but not always identical).
- **LittleGPTracker / picoTracker import (agreed 2026-11-19):** 8-track handheld trackers with the same song → chain → phrase model as TrackWerk, so songs come across nearly one-to-one, samples and instruments included. - **FamiTracker import (agreed 2026-11-19):** NES songs (.ftm), 5 channels, after the Game Boy and NES chips item so they sound like the NES. - **Record notes live (agreed 2026-11-19):** play a MIDI keyboard (or the buttons) while the song runs and the notes are written into the phrase in time, plus step recording (one note per step, the cursor moving on). **Shortcut:** ChooChooTracker (MIT, read 2026-11-19) `chipnomad_lib/midi/midi_recording.*`: real-time and step recording, a delay command when a note lands between steps, notes handed from the audio thread to the screen through a lock-free queue.
- **MIDI file export (agreed 2026-11-19):** save the song's notes as a `.mid` (one MIDI track per tracker track, program changes, tempo), to continue in a DAW. **Shortcut:** ChooChooTracker (MIT, read 2026-11-19) `chipnomad_lib/export/export_midi.cpp` on its `smf_file.*` writer. The counterpart of MIDI file import.
- **16 tracks (agreed 2026-11-18, redesigned 2026-11-19):** a song is either 8-track or 16-track; there is no device setting for it. **File extension:** 8-track songs stay `.ptp`; 16-track songs save as **`.pt16`** (any extension length works on Windows, macOS, Linux, Android and FAT32/exFAT cards with long names). Older TrackWerk versions list only the extensions they know, so they never see a `.pt16` and can't open or damage it. The app opens both and switches to the song's track count as it loads. **NEW** asks 8 or 16 tracks in a small box. **PROJECT** gains a TRACKS 8/16 row next to the song's name: 8 → 16 turns tracks 9-16 on and the song saves as `.pt16` from then on (the earlier `.ptp` stays as it was); 16 → 8 is allowed only after a warning when tracks 9-16 hold anything or phrases / chains above FF are used, since accepting deletes them; a 16-track song may stay `.pt16` even with tracks 9-16 empty. In an 8-track song tracks 9-16 show greyed (see wide mode). **Same name, two extensions:** `Song.ptp` and `Song.pt16` may exist side by side; every name check (save-over question, COLLECT, rename) and the autosave treat `.pt16` exactly as `.ptp` today, each within its own extension, and the autosave writes the extension of the song that is open. **Pools (16-track songs only):** 512 phrases and 512 chains (8-track songs keep 256), 256 instruments and 256 tables (still two hex digits). Screens with room show phrase and chain ids as three hex digits (CHAIN's PH column, PHRASE and CHAIN titles; leading zero dimmed); SONG keeps two characters by letting the first one run on past F: `G0`-`VF` mean `100`-`1FF` (G = 10 … V = 1F), drawn with the app's own letters. 512 is the ceiling (two characters can't name more). Pattern-tracker imports must merge identical phrases and report songs that don't fit. **Opening a `.pt16` on a weak device** (the Linux handhelds: Brick, RGB20S, Miyoo Mini/Plus and the other PortMaster targets) first shows a box explaining the device may not play it fully, with sound problems, if the CPU runs out; A opens it, B leaves the open song exactly as it was. Windows, Linux desktop and Android open it directly. **Pages:** SONG, MIXER and any screen whose tracks don't fit (on 4:3, or past the screen's width) show them a page at a time; moving the cursor past the last track on the page turns to the next page, the way the screen map's letters move between screens, and a small arrow on the left or right shows there is another page that way. Open for the spec: what the preview lane (today track 8 + 1) becomes, MIDI and stems for tracks 9-16, and the voice count (16 song voices + preview). Mapped earlier: about 120 places in the code assume 8 tracks; the song format already allows any number of tracks, and phrase / chain refs are plain integers. **Five effect columns (agreed 2026-11-19, 16-track songs only):** PHRASE gets FX4 and FX5 in `.pt16` songs (8-track songs keep three). Wide mode shows all five; on 4:3 FX1-3 stay as today and FX4-5 sit on a small second column page reached by moving the cursor past FX3, with the paging arrow. The three fixed fields (`fx1`..`fx3`, about 20 files: sequencer, `AUS`/`AUF` pairing per column, copy/paste column numbers, Drumlab, HARMONY, help, importers, piano roll, automation recording) become a list. Tables remain the way to run more commands per note.

- **Synth voices on spare cores (future, agreed 2026-11-18):** the audio thread stays in charge; each block, synth voices go on a work list that idle helper threads may take, and the audio thread takes whatever is left itself, so it never waits on a helper. Each voice renders into its own buffer and the mix sums them in today's fixed order, so the output is bit-identical with any number of helpers. With no spare cores (or the setting off) nothing changes. Needs: synth voices rendered per block instead of per sample (`engine-mix.cpp` calls `synth.next` per sample today), per-voice meters, scopes and send sums merged after, and timing tests on every platform. Build after the sound items and New Note Action, and only when real devices run short of CPU (PERFORM's PEAK meter). Offline renders could use every core first, with no timing risk.
